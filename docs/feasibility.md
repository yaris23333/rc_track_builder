# RC Track Builder 前端分析与赛道编辑器可行性评估

> 分析对象：https://rctrackbuilder.com/ （版本 0.5.0，构建号 afbb1318）
> 分析范围：公开可访问的页面、静态资源、JS bundle、客户端存储与导出逻辑。
> 结论日期：2026-11-05

---

## 0. 结论先行

**能做，而且核心并不难。**

参考站本质上是一个「用图片铺格子的画板」，不是真正的赛道数据模型：

- 默认 7×4 网格，每格 100px；
- 8 种瓦片，全部是 1×1 的透明 PNG；
- 拖拽/点击放置，旋转、翻转、删除、多选；
- 保存/加载 JSON 文件，导出 PDF；
- 没有后端、没有账号、没有数据库、没有自动保存；
- 没有端口/连接关系、没有闭环校验、没有长度计算、没有物料清单。

所以「复刻一个同款」大约是 **3–5 人日** 的工作量；做一个真正好用、功能更丰富的赛道设计工具，建议按 **15–25 人日** 规划（1 人 3–5 周，2 人 2–3 周）。真正的难点不在网格，而在：

1. 赛道语义（瓦片端口、连接、闭环、方向、比例尺）；
2. 可施工输出（1:1 打印、PDF、BOM、DXF）；
3. 移动端/触屏交互；
4. 把「画得出来」变成「验得正确、造得出来」。

## 1. 实际访问到的内容

### 1.1 路由与页面

| 路由 | 内容 |
|---|---|
| `/` | 赛道网格编辑器（核心） |
| `/race-planner` | 比赛日时间规划器（班级、参赛人数、轮次、赛程估算、导出 PDF） |
| `/shock-hole-calculator` | 避震活塞孔流量计算器（孔数/孔径换算） |

没有发现：

- 后端 API、登录、数据库、云存储；
- `sitemap.xml`、PWA manifest、Service Worker；
- 开源许可证或公开源码仓库；
- 任何服务端保存赛道的能力。

### 1.2 技术栈

- **Next.js App Router**，Turbopack 构建；
- React + Tailwind CSS（大量 `bg-primary`、`base-200` 等 daisyUI 风格类名）；
- 纯 DOM + CSS Grid 渲染，**不是 Canvas/WebGL**；
- 可选 **Tauri** 桌面端（代码里有 `__TAURI__` 判断和原生文件对话框）；
- PDF：`html2canvas` + `jsPDF`，2 倍截图画布后按 A4 等比缩放；
- 统计：GA4 + Google Tag Manager。

### 1.3 资源体积

| 资源 | 情况 |
|---|---|
| JS | 约 988 KB（未压缩，含框架与 PDF 库） |
| CSS | 约 92 KB |
| 瓦片 | 8 张 1024×1024 透明 PNG，合计约 108 KB |
| 字体 | 2 个 woff2 预加载 |

PDF 相关库占了 bundle 的很大一部分；核心编辑器组件本身只有约 42 KB（压缩前）。

### 1.4 网格与瓦片

- 初始 `gridWidth = 7`、`gridHeight = 4`；
- 单元格 `100px`，网格内边距 `16px`；
- 缩放 `cellSizeScale` 范围 `0.5–3.0`，通过 CSS `transform: scale()` 实现；
- 支持上下左右增删行列；
- 瓦片定义支持 `width/height`，但当前 8 种全部是 `1×1`：
  - Straight、Single、Double small、Rollers big、Rollers small、Table、90、Start/Finish；
- 瓦片图片是透明线稿 PNG，放在白色底上显示；
- 旋转 `0/90/180/270`，支持水平/垂直翻转；
- 多选：Ctrl/Cmd + 点击，浮动工具条做旋转/翻转/删除。

### 1.5 数据模型与存档格式

每个格子：

```ts
{
  tileType: string;          // "straight" | "90_1x1" | ...
  rotation: number;          // 0 | 90 | 180 | 270
  flipH: boolean;
  flipV: boolean;
  tileOrigin?: { row: number; col: number }; // 多格瓦片的原点
  isOccupied: boolean;       // 被多格瓦片覆盖的格子
}
```

存档 JSON：

```json
{
  "version": "1.0",
  "gridWidth": 7,
  "gridHeight": 4,
  "grid": [
    [
      { "tileType": "straight", "rotation": 0, "flipH": false, "flipV": false },
      { "tileType": "empty", "rotation": 0, "flipH": false, "flipV": false }
    ]
  ]
}
```

保存/加载通过浏览器下载/上传 `.json` 文件；Tauri 环境下走原生文件对话框。**没有 localStorage、IndexedDB 或自动保存**，刷新即丢。

### 1.6 参考站的功能边界

已实现：

- 拖拽放置、点击放置、格子内拖动；
- 旋转、水平/垂直翻转、删除、清空；
- 多选；
- 增删行列；
- 缩放；
- 保存/加载 JSON；
- 导出 A4 PDF；
- 深色模式（跟随系统）。

没实现 / 做得很弱：

- 撤销/重做入口（代码里有历史栈，但没有 UI 或快捷键触发）；
- 键盘快捷键；
- 自动保存、项目列表、版本历史；
- 赛道连通性校验、闭环检测；
- 起终点方向、行驶方向；
- 比例尺、真实长度、面积；
- 物料清单（BOM）、1:1 打印、CNC/DXF；
- 多层/立交桥/跳台高差；
- 图片底图描图；
- 移动端适配（实测 390px 宽度下侧栏挤占、按钮被裁切、网格横向溢出）；
- 分享链接、云端项目、协作。

### 1.7 关键判断

参考站把赛道当成「一张由 8 种图块拼成的图」，而不是「一个有拓扑关系的赛道」。因此：

- 它很容易做，但天花板也低；
- 你的机会不是再做一个同款，而是做「**可验证、可施工**」的赛道设计器。

## 2. 可行性判断

### 2.1 技术风险：低

核心编辑器是典型的 2D 网格编辑器：

- 网格坐标 ↔ 屏幕坐标；
- 瓦片放置/移动/旋转/翻转；
- 选择、框选、剪贴板；
- 视口平移缩放；
- 撤销重做；
- 序列化；
- 导出。

这些都有成熟做法。真正的工程量在细节打磨和赛道语义。

### 2.2 产品风险：中

需要提前定清楚：

1. **一格代表多大真实尺寸？**（1 ft / 2 ft / 1 m）
2. **瓦片是否有端口和方向？**（决定能否做连通性校验）
3. **赛道是单车道还是多车道？**（影响端口模型和长度计算）
4. **要不要立交/跳台高差？**（决定 2D 还是 2.5D 数据模型）
5. **输出优先级：** 打印 PDF / BOM / DXF / 分享链接？

建议先做 2D 单层、单车道、带端口的版本，把闭环和长度跑通，再扩展多层。

### 2.3 工作量估算

| 阶段 | 内容 | 人日 |
|---|---|---|
| P0 | 需求确认、瓦片规格、交互原型 | 1–2 |
| P1 | 编辑器核心：网格、调色板、放置/移动/旋转/翻转/删除、多选、撤销重做、平移缩放、自动保存、JSON 导入导出、响应式 | 4–6 |
| P2 | 赛道语义：端口、连接图、闭环校验、起终点方向、比例尺、长度/面积 | 4–6 |
| P3 | 输出：PNG/PDF、1:1 分页打印、BOM、模板、分享 | 4–6 |
| P4 | 打磨：移动端/触屏、测试、性能、可访问性 | 3–5 |
| **合计** | **可用的 v1** | **16–25 人日** |

如果只做「参考站同款 + 少量改进」，**5–8 人日** 即可；  
如果加 3D 预览、实时协作、云端账号、CNC 导出，再加 **15–30 人日**。

## 3. 建议的技术方案

### 3.1 技术栈

推荐：

- **React 19 + TypeScript + Vite**（纯客户端，静态部署）
- **Tailwind CSS + shadcn/ui**（或 daisyUI，看审美）
- **Zustand + Immer** 管理文档与 UI 状态
- **SVG 渲染** 网格与瓦片
- **Pointer Events** 自定义拖拽（兼容鼠标/触屏/触控笔）
- **zod** 做存档 schema 校验与版本迁移
- **idb / localforage** 做 IndexedDB 自动保存
- **jsPDF + svg2pdf.js** 或浏览器打印 CSS 做 PDF
- **Vitest + Playwright** 做单元与端到端测试
- 部署：Cloudflare Pages / Vercel / Netlify

不建议：

- 用 Next.js 只为了一个编辑器（除非还要做官网 SEO、账号、服务端分享）；
- 用 DOM CSS Grid 渲染大网格（参考站的做法，格子多了会卡）；
- 用 `html2canvas` 导出（慢、脆、清晰度差）；
- 用 HTML5 Drag and Drop 做主交互（移动端基本不可用）。

### 3.3 数据模型

```ts
type Rot = 0 | 90 | 180 | 270;

interface Port {
  x: number;              // 瓦片局部坐标（格）
  y: number;
  dir: 'N' | 'E' | 'S' | 'W';
  lane: number;           // 多车道时使用
}

interface TileDef {
  id: string;
  name: string;
  category: 'straight' | 'curve' | 'feature' | 'start' | 'accessory';
  size: { w: number; h: number };       // 占几格
  ports: Port[];                        // 连接口
  centerline: PathPrimitive[];          // 中心线，用于算长度
  physical: { lengthMm: number; widthMm: number };
  svg: string;                          // 或 React 组件
}

interface PlacedTile {
  uid: string;
  defId: string;
  x: number;                            // 原点格坐标
  y: number;
  rot: Rot;
  flipX: boolean;
  layer: number;                        // 0 地面，1 桥
}

interface TrackDoc {
  schemaVersion: 1;
  unit: 'mm' | 'in';
  cellMm: number;                       // 一格的真实尺寸
  tiles: PlacedTile[];                  // 稀疏存储
  meta: {
    name: string;
    author?: string;
    notes?: string;
    createdAt: string;
  };
}
```

相比参考站的「二维稠密数组」，推荐**稀疏存储 + 派生占位索引**：

- 网格可以无限扩展；
- 多层/立交更好表达；
- 增删行列不需要整体搬数组；
- 撤销重做只存命令，不存整张网格快照。

### 3.4 核心算法

1. **占位与碰撞**  
   瓦片 footprint 经旋转/翻转后映射到全局格；与已有瓦片求交，重叠则禁止放置或高亮。

2. **端口变换**  
   端口局部坐标先翻转、再旋转，得到全局坐标和方向；相邻格子的对面端口必须匹配。多车道时按 `lane` 匹配。

3. **连接图**  
   以瓦片实例为节点、端口匹配为边，构建邻接表；用 DFS/并查集找连通分量、环、悬挂端口。

4. **闭环校验**  
   所有端口都有匹配 + 恰好一个环 + 起终点在环上 + 方向一致。给出可视化错误：红色端口、断点列表、点击定位。

5. **长度计算**  
   每块瓦片的中心线长度（直线/圆弧）按比例尺累加；圆弧长 `r × θ`；多车道按车道中心线分别计算。

6. **BOM**  
   按 `defId` 聚合数量、总长度、占地面积；导出 CSV / PDF 表格。

7. **渲染裁剪**  
   只渲染视口内的瓦片；缩放用 `transform`；悬停/选择用独立 overlay，避免全量重渲染。

### 3.5 交互设计

桌面端：

| 操作 | 交互 |
|---|---|
| 放置 | 从调色板拖入；或选中瓦片后点击格子 |
| 移动 | 拖动已放置瓦片；Alt+拖动复制 |
| 旋转 | `R` / `Shift+R`；工具条按钮 |
| 翻转 | `F` / `Shift+F` |
| 删除 | `Delete` / `Backspace` |
| 撤销/重做 | `Ctrl/Cmd+Z` / `Ctrl/Cmd+Shift+Z` |
| 平移 | 空格+拖动 / 中键拖动 |
| 缩放 | 滚轮以光标为中心 / 双指捏合 |
| 多选 | 框选；Shift 追加；Ctrl/Cmd 点选 |
| 复制粘贴 | `Ctrl/Cmd+C` / `V` |
| 属性 | 双击瓦片打开右侧面板 |

移动端：

- 调色板改为底部抽屉；
- 单指拖动 = 平移画布，长按/选中后拖动 = 移动瓦片；
- 双指捏合缩放；
- 工具栏大按钮，避免悬浮小图标。

### 3.6 输出方案

- **PNG**：直接把 SVG 序列化后画到 Canvas，2–3 倍分辨率；
- **PDF**：从模型生成专用打印 SVG（A4/A3），用 `svg2pdf.js` 或浏览器打印，支持标题、图例、比例尺、BOM；
- **1:1 打印**：按 `cellMm` 计算每页覆盖的格子数，分页输出并带裁切标记/重叠边，用于实地放样；
- **DXF/SVG**：输出瓦片轮廓/中心线，供 CNC 或激光切割；
- **BOM**：瓦片数量、总长度、面积、建议采购量；
- **JSON**：带 `schemaVersion`，支持迁移；
- **分享链接**：小布局用 LZ-string 压缩到 URL hash；大布局/多人用后端或 Supabase。

### 3.7 测试重点

- 旋转/翻转的坐标变换是否可逆；
- 多格瓦片（2×1、2×2、L 形）的占位与端口；
- 闭环检测的边界情况（自交、双环、悬挂端）；
- 长度计算的圆弧/比例尺；
- 撤销重做与自动保存的一致性；
- 触屏拖拽、缩放、误触；
- 导出文件的尺寸与清晰度。

## 6. 风险与合规

### 6.1 知识产权

- 参考站的瓦片图片、Logo、名称、整体视觉都受版权/商标保护，**不要直接下载复用**；
- 功能思路可以借鉴，但建议 clean-room 重写，使用自己的 SVG 瓦片、自己的名称和视觉；
- 其 `robots.txt` 声明了 `ai-train=no`；本次只是按你的要求做公开前端技术分析，不应把其资源用于训练或再分发；
- 未发现开源许可证，不能假设可以复制代码。

### 6.2 技术风险

| 风险 | 应对 |
|---|---|
| 多格瓦片旋转容易出错 | 用矩阵变换 + 单元测试覆盖所有旋转/翻转组合 |
| 移动端 HTML5 DnD 不可用 | 用 Pointer Events 自定义拖拽 |
| PDF 导出模糊/错位 | 从模型生成打印 SVG，不用 html2canvas |
| 大网格卡顿 | SVG 视口裁剪；超过 3–5k 瓦片切换 Canvas/Konva |
| 需求蔓延 | 锁定 MVP，多层/协作/3D 放 v2 |
| 比例尺不统一 | 文档级 `cellMm`，所有长度派生计算 |

## 7. 建议的下一步

在开工前确认 3 件事：

1. **一格代表多大真实尺寸？** 建议默认 `1 格 = 1 m` 或 `2 ft`，可配置；
2. **输出优先级？** 打印 PDF / BOM / DXF / 分享链接，先做哪个；
3. **主要使用设备？** 桌面为主，还是平板/手机也要好用。

我的建议默认值：
